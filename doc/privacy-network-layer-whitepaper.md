# Network-Layer Transaction Privacy in Pirate Chain: Privacy-Peer Relay Restriction and Rotating I2P Relay Identities

**A system description and comparative analysis**

**Scope:** [TreasureChest/src/net.cpp](../src/net.cpp), [net.h](../src/net.h), [i2p.cpp](../src/i2p.cpp), [wallet/wallet.cpp](../src/wallet/wallet.cpp), [rpc/net.cpp](../src/rpc/net.cpp), [qt/rpcconsole.cpp](../src/qt/rpcconsole.cpp)
**Date:** August 2026

---

## 1. Motivation

Pirate Chain's on-chain privacy is complete by construction: every transaction is shielded (Sapling, Ironwood), so amounts, senders, and recipients are cryptographically hidden regardless of network behavior. That completeness narrows, rather than eliminates, the remaining attack surface. If the cryptography hides *what* moved, the only thing left for an adversary to learn is *where a transaction came from* — which network peer, and by extension which IP address or persistent network identity, first announced it.

This is a well-studied problem across the broader cryptocurrency ecosystem, independent of what a chain's transactions actually contain. A node that broadcasts a locally-created transaction to every connected peer, in the same relay round, gives a well-positioned observer (or a set of colluding peers) a straightforward heuristic: whoever announced it earliest, or announced it to the fewest hops, is probably the origin. This document describes two complementary systems built to close that gap for Pirate Chain's P2P layer, and situates them against how comparable privacy-focused projects — Bitcoin, Monero, Grin, Firo, Zcash, Dash, Dero, and Zano — have approached the same problem.

The two systems:

1. **Privacy-peer relay restriction** — locally-originated transactions (wallet sends, `sendrawtransaction`, the nSPV broadcaster, CC-module submissions) are, by default, relayed only to peers reachable over Tor or I2P, never to plain clearnet peers, removing raw-IP exposure for the common case.
2. **Rotating I2P relay-pool identities** — a pool of short-lived, burn-after-use I2P destinations used exclusively to relay locally-originated transactions, separate from the node's permanent I2P identity, closing a linkability gap that Tor's architecture doesn't have but I2P's does.

## 2. System 1: Privacy-peer relay restriction

### 2.1 The problem

Prior to this work, `CWalletTx::RelayWalletTransaction()` and every other local-broadcast path funneled into `RelayTransaction()`, which pushed the transaction's `INV` to every connected peer in the same relay round, subject only to ordinary trickle-delay jitter. A clearnet-connected observer — including a passive one running an unremarkable full node — could see the raw IP that first announced any given transaction.

### 2.2 Design

`RelayTransaction()` now takes an `fLocalOrigin` flag, threaded through from every local-broadcast call site: `CWalletTx::RelayWalletTransaction()`, `sendrawtransaction`, the nSPV full-node broadcaster, and CC-module transaction submission. Transactions relayed on behalf of another peer (i.e. ordinary network gossip) are untouched — they still flood to all peers as before, which is correct: restricting *that* traffic would only slow propagation without buying any privacy, since the transaction is already public by the time a peer is relaying it onward.

For a locally-originated transaction, the peer-selection loop consults two pure, independently-tested functions:

```cpp
bool IsPrivacyPeer(bool fInbound, const CNetAddr& addr)
```
([net.cpp:497](../src/net.cpp#L497)) — true for any outbound Tor peer, and for I2P peers in *either* direction. The asymmetry is deliberate: an inbound Tor connection always arrives loopback-forwarded from the local Tor daemon, so there is no real `.onion` address to check on the inbound side — only outbound Tor connections carry a verified remote identity. I2P's SAM `STREAM ACCEPT` protocol, by contrast, delivers the genuine remote I2P destination on inbound connections too, so both directions qualify.

```cpp
bool ShouldRestrictRelayToPrivacyPeers(bool fLocalOrigin, bool fPrivateTxRelayEnabled, int nPrivacyPeers, bool fAllowFallback)
```
([net.cpp:511](../src/net.cpp#L511)) — when the transaction is locally-originated, the feature is enabled (`-privatetxrelay`, default on), and at least one privacy peer is currently connected, relay is restricted to the `IsPrivacyPeer` subset. If zero privacy peers are connected, the function fails open to all peers *unless* the operator has set `-privatetxrelayfallback=0`, in which case the transaction simply isn't relayed this round rather than ever touching a clearnet peer — it will be retried on the next relay attempt or the wallet's periodic rebroadcast once a privacy peer connects.

This closes the raw-IP-exposure gap for the overwhelming common case: a clearnet-only observer, not itself a Tor/I2P connection, can no longer see which node originated a transaction at all.

### 2.3 What it doesn't solve on its own

Restricting *which* peers see a transaction first says nothing about *how many* of them do, or in what pattern. Every currently-connected privacy peer still receives the `INV` in the same relay round, and a directly-connected peer can still observe "I was among the first told" for that one transaction. On its own, that observation is a privacy-relevant signal only if it can be *linked* to something else — the real IP (already closed by System 1) or a persistent identity that lets the same peer connect this observation to a future one.

For Tor, no such persistent identity is exposed to the peer in the first place (§3.1), so there is nothing for a Tor peer to link a "first told" observation to, regardless of how long the connection stays open or how many transactions cross it. For I2P, prior to System 2, the SAM session's persistent destination *was* exactly that linkable identity — a peer that noticed "I was told first" today, and noticed the same I2P destination again next week, could build a lasting behavioral profile from it. That is the specific gap System 2 closes, not merely mitigates: see §3 for the mechanism, and §5 for the one precise, bounded case where linkability can still reappear.

## 3. System 2: Rotating I2P relay-pool identities

### 3.1 Why I2P needs something Tor doesn't

System 1 treats Tor and I2P as interchangeable "privacy peer" categories. They are not equivalent once a peer is actually connected.

An outbound Tor connection reveals no persistent identity to the remote peer: the remote sees the connection arrive through their own local Tor daemon's loopback forwarding, with no stable, attributable identity behind it from one circuit to the next (`-proxyrandomize`, on by default, forces a fresh circuit per outbound connection — see §5 for how this relates to Biryukov & Pustogarov's Tor-circuit-correlation research). Repeated outbound Tor connections from the same node do not, by themselves, present the same face to the network twice.

I2P's SAM protocol works differently. `Session::Connect()` ([i2p.cpp:194-243](../src/i2p.cpp#L194-L243)) issues `STREAM CONNECT ID=<session_id> DESTINATION=<remote> SILENT=false` — the destination the remote end learns is tied to the *session's* keypair, not to the individual stream. Every connection made through one SAM session presents the same I2P destination to every remote peer it talks to, for as long as that session lives. A node that relays ten transactions through its one persistent I2P identity gives any single colluding I2P peer — or several colluding peers comparing notes — ten linkable data points tied to the same address, even though the underlying transaction contents remain fully shielded.

Notably, this is not a hypothetical concern invented for this design: Monero's own anonymity-network documentation identifies exactly this failure mode independently — *"If a single I2P/Tor stream is used 2+ times for transmitting a transaction, the operator of the hidden service can conclude that both transactions came from the same source"* — and Monero's mitigation for it is to rely on the underlying network's own circuit churn (Tor circuits rotate roughly every 10 minutes on their own; each new circuit carries a fresh identity). That mitigation works for Tor because Tor's architecture gives fresh identity per circuit for free. It does not work for I2P, because an I2P SAM session's destination does not rotate merely by opening new streams — the identity lives at the session level, and nothing rotates it except destroying and regenerating the session itself. This is the specific gap System 2 closes.

### 3.2 Two-tier identity model

Rather than modifying the node's existing I2P identity, the design adds a second, independent tier alongside it:

- **Primary identity** — the existing, single, permanent `m_i2p_sam_session`, unchanged. It continues to serve general connectivity: inbound accept, outbound peer discovery, relaying *other* peers' transactions, address-manager participation, and (for operators who want it) acting as a stable, publicly-documented address. The primary identity is **never** used to relay a locally-originated transaction, so it is never linkable to a specific transaction — and because it's never used that way, it never needs a "seed node" exemption or an on/off toggle. It simply never changes.
- **Relay pool** — a set of additional, independently-generated I2P identities (`g_i2p_relay_pool`) that exist for exactly one purpose: relaying the node's own locally-originated transactions, one identity per transaction, then retiring.

Every connection is tagged with which identity it belongs to (`m_i2p_pool_idx` on `CNode`/`CNodeStats`, surfaced via `getpeerinfo`'s `i2p_identity` field as `"primary"` or `"pool-N"`, and in the Qt Peers detail pane). `RelayTransaction()`'s local-origin path ([net.cpp:3459](../src/net.cpp#L3459)) restricts I2P eligibility to peers on the *currently selected* pool identity only — primary-identity I2P peers, and every other pool identity's peers, are excluded from that specific relay round.

### 3.3 Lifecycle

Each pool slot moves through a small state machine, driven by a periodic scheduler tick (`TickI2PRelayPool()`, [net.cpp:2672](../src/net.cpp#L2672), every 60 seconds) and a dedicated top-up thread (`ThreadI2PPoolTopUp()`, [net.cpp:2874](../src/net.cpp#L2874)):

- **WARMING** — a freshly (re)generated identity. I2P tunnel construction and leaseset publication take real wall-clock time, and — separately — a slot with built tunnels but zero peers has nothing to relay to. A slot needs both: a warmup deadline to elapse (`I2P_POOL_WARMUP_PERIOD`, 180s) *and* to have accumulated at least `I2P_POOL_MIN_PEERS_FOR_READY` (2) live connections, via ordinary outbound dialing or inbound acceptance, before promotion (`ShouldPromoteI2PPoolIdentityToReady`, [net.cpp:590](../src/net.cpp#L590)).
- **READY** — warmed, peered, and eligible for selection.
- **ACTIVE** — selected for a specific transaction. `SelectI2PPoolIdentityForRelay()` ([net.cpp:558](../src/net.cpp#L558)) round-robins among `READY`-with-peers slots; if none are available it degrades to reusing the `ACTIVE` slot with the soonest drain deadline rather than dropping the relay entirely. Once selected, the slot is retired after a bounded drain window (`I2P_POOL_DRAIN_PERIOD`, 10 minutes — comfortably inside the 15-minute `mapRelay` cache TTL used to serve `GETDATA`), giving the peer time to actually pull the transaction before the identity disappears.
- **Retirement and regeneration** — peers tied to the retiring slot are disconnected, its on-disk key file is deleted, and a fresh identity is generated in its place (`ActivateI2PPoolSlot()`, [net.cpp:2639](../src/net.cpp#L2639)), reusing the existing `Session::CreateIfNotCreatedAlready()` machinery unmodified. Retirement is triggered by whichever comes first: the identity was used and its drain window elapsed (burn-after-use), or a backstop expiry timer elapsed regardless of use (`ShouldRetireI2PPoolIdentity`, [net.cpp:583](../src/net.cpp#L583)) — so an identity that's warmed but never selected doesn't live forever either.

Burn-after-use, not pure time-based rotation, is the core property: retiring an identity immediately after it relays one transaction gives *per-transaction* unlinkability. A purely time-windowed rotation (e.g. "generate a new identity every hour") would still let every transaction relayed within that hour share one identity — exactly the multi-transaction linkability this system exists to prevent.

### 3.4 Staggered backstop expiry

If every backstop expiry were drawn independently and uniformly, there would be a real (if small) chance several identities' timers land close together, causing a burst of simultaneous disconnect/reconnect that's more disruptive — and more observable as a distinctive pattern — than staggered rotation. `ComputeI2PPoolStaggeredExpiry()` ([net.cpp:524](../src/net.cpp#L524)) draws a candidate uniformly from a lifetime window and, if it lands within a minimum margin of any other currently-live slot's expiry, pushes it to the nearest safe edge (clamping back into the window if that push would violate the floor or ceiling). This is a pure, independently-tested function, not a probabilistic hope.

### 3.5 Sizing and burst capacity

Two runtime-configurable parameters govern steady-state pool behavior: `nI2PPoolMinReserve` (how many identities are kept warmed and ready) and `nI2PPoolMaxSize` (the ceiling for burst replenishment). These interact with the staggering window in a way worth stating precisely: a lifetime window of width *W* with minimum stagger margin *S* can hold at most `W/S + 1` mutually-spaced identities before the clamp-to-boundary behavior forces collisions. Reserve/max size and the lifetime window must be sized together, not independently.

Reserve size also directly determines **burst-transaction depth**: because selection always exhausts `READY` slots before reusing an `ACTIVE` one, the number of transactions that can be sent in rapid succession while each still receives a distinct, never-reused-in-that-burst identity is bounded by how many slots are `READY`-with-peers at the moment the burst begins — which is to say, by the reserve size, for a burst faster than the warmup cycle can replenish. A larger reserve is a direct, quantifiable improvement to unlinkability under bursty usage (e.g. auto-consolidation or auto-sweep firing several transactions close together), not just a resource-usage knob.

### 3.6 Fairness and observability

An operational bug found and fixed during implementation is worth documenting as part of the system's description, since it shaped the final design: the top-up thread originally processed under-peered slots in a fixed ascending-index order, which — under I2P address scarcity — let lower-indexed slots systematically win every scarce dial candidate first, permanently starving higher-indexed slots rather than merely being unlucky once. The fix (a Fisher-Yates shuffle of the candidate list each tick) gives every under-peered slot a fair shot at each tick's available candidates. The pool subsystem also emits structured `LogPrint("net", ...)` diagnostics at every lifecycle transition, so an operator can observe warmup, promotion, selection, and retirement directly from `-debug=net` output rather than needing to reconstruct state from `getpeerinfo` polling.

### 3.7 Per-identity connection accounting

A second-order consequence of running multiple local I2P identities: the per-source-IP inbound connection cap (`MAX_INBOUND_FROMIP`, an eclipse-attack mitigation) originally counted connections from a given remote address globally, across every local identity at once. That's correct for every other network — a node has exactly one local address on IPv4, IPv6, or Tor — but wrong for I2P once a node presents several independent local destinations by design: a remote peer legitimately connecting to both the primary identity and a pool identity is exactly the intended multi-identity behavior, not abuse, and shouldn't count against itself. `ShouldCountTowardInboundFromIPCap()` ([net.cpp:476](../src/net.cpp#L476)) scopes the cap per (remote address, local identity) pair for I2P specifically, leaving the original global-per-address behavior untouched everywhere else.

## 4. Comparative analysis

The underlying problem — an adversary correlating "who first announced transaction X" — is not unique to this chain. It has been studied, shipped, contested, and in some cases explicitly rejected across the ecosystem. The table below situates this system's design choices against that prior art.

| Project | Network-layer mechanism | Status | Key distinction from this system |
|---|---|---|---|
| **Bitcoin** (BIP156 "Dandelion") | Stem phase (single-path relay, random hop count), then fluff (normal flood) | **Proposed, never merged** — [bitcoin/bitcoin#13947](https://github.com/bitcoin/bitcoin/pull/13947) closed without merging over incomplete stempool design and unclear RBF/transaction-chain behavior | Stem/fluff diffuses relay-timing inference across the whole peer graph; it does not address persistent-identity linkability the way identity rotation does, and is a genuinely complementary technique — see §6. |
| **Bitcoin Core** (shipped instead) | Simultaneous-delay `INV` announcement (PR #13298); `-proxyrandomize` SOCKS5 stream isolation (PR #5911, 2015) | **Shipped** | Narrower timing/circuit-correlation fixes, not full stem/fluff routing. This system's `-proxyrandomize` equivalent is already in place (§5). |
| **Monero** | Dandelion++ (shipped April 2020, v0.16); optional native Tor/I2P anonymity-network integration (`--tx-proxy`) | **Shipped** | Monero's own docs document the exact stream-reuse-identity-linkability problem this system's rotation solves, but mitigate it only by relying on the underlying network's circuit churn (roughly two new outbound connections every 5 minutes) rather than an explicit rotation-with-warmup abstraction. That reliance is sound for Tor (fresh circuit ⇒ fresh identity, structurally) but does not hold for I2P (fresh stream ⇒ same session identity) — the specific gap this system's pool exists to close. That same fixed, five-minute-reused outbound fan-out (two connections) is also a smaller anonymity set for an adversary to occupy than this system's actively-replenished reserve presents — a separate, more mundane advantage of the larger pool, distinct from anything about identity rotation itself. Monero's anonymity-network integration has separately been the target of a real, named academic attack, **ProxyMark** ([ACM Web Conference 2024 companion proceedings](https://dl.acm.org/doi/10.1145/3589335.3651487)), which traces a target's Tor circuit back to its real IP via watermarking through malicious entry relays after identifying it as an origin-transaction relay. That technique operates on the Tor circuit itself, below the destination-identity layer — it is unaffected by whether the destination address is reused or freshly rotated, and this system does not defend against it either (§5). |
| **Grin** (MimbleWimble) | Dandelion++ | **Shipped** | Stem-phase relay also lets transactions aggregate before fluff, since MimbleWimble transactions merge losslessly — a cryptographic reinforcement unavailable to a Sapling/Orchard/Ironwood transaction model. |
| **Firo** | Dandelion++ | **Shipped**, positioned explicitly as an alternative to requiring Tor/I2P | Represents the opposite design philosophy from this system: obfuscate the relay graph itself rather than requiring an anonymity network underneath. See §6 for why the two approaches are complementary rather than substitutes here. |
| **Zcash** (zcashd) | None | **Not implemented.** Official documentation acknowledges the gap directly and recommends Tor as an external, operator-configured mitigation; an I2P integration issue ([zcash/zcash#1111](https://github.com/zcash/zcash/issues/1111)) has been open since 2016 | This system implements, natively and by default, exactly what Zcash's own documentation recommends as manual operator discipline — and extends it with I2P-specific identity rotation that no zcashd deployment (Tor-only guidance) addresses even in principle. |
| **Dash** | None for ordinary tx relay | **Not implemented** | InstantSend's quorum-based signature aggregation (DIP-0006, LLMQs) reduces which masternodes are visible as *signers* for an `islock`, but doesn't address which node originated the underlying transaction on ordinary P2P relay — a different part of the pipeline entirely. |
| **Dero** | TLS-encrypted P2P transport (self-signed certificates over KCP/UDP) | **Shipped**, but explicitly **does not hide IP addresses** — the project's own documentation states the source IP remains visible at the network layer; TLS protects packet contents and integrity only. Tor support exists only as a manual, operator-configured SOCKS proxy, and there is no Dandelion-style relay obfuscation | Illustrates a meaningfully different design point: strong transport confidentiality with no attempt at origin-hiding by default. Dero's most publicized deanonymization issue (a 2024 disclosure involving ElGamal-ciphertext randomness reuse) was a cryptographic/application-layer flaw in encrypted message payloads, not a network-layer origin-linking attack — a useful reminder that "privacy coin" claims span at least two independent layers (on-chain content privacy and network-layer origin privacy), and strength in one says nothing about the other. |
| **Zano** | None (Dandelion++ deliberately rejected); built-in Tor client implemented, then disabled | **Explicitly rejected as a design choice**, not merely unimplemented. The Zano team's stated reasoning: in a P2P network with a nontrivial fraction of monitoring nodes, Dandelion-style stem routing gives a false sense of protection rather than a real one, since an adversary controlling enough stem-path nodes defeats it regardless. Their built-in Tor integration was disabled after encountering severe transaction-propagation failures — circuits not reliably completing before a transaction needed to broadcast | The most direct real-world validation of a risk this system was designed around: Zano's Tor failures are consistent with treating anonymity-network connectivity as available on demand rather than pre-warmed. This system's `READY`-gated selection — never selecting an identity until it has *already* built tunnels and accumulated live peers — is a structural answer to exactly that failure mode, at the cost of the added complexity §3 describes. Zano's skepticism about Dandelion-class defenses against a well-resourced adversary is a fair critique this system does not claim to fully answer either — see §5. |

## 5. What this system does and does not defend against

**Defends against:**
- A passive clearnet observer learning that a given IP originated a given transaction (System 1).
- A single I2P peer, or a small colluding set — however many nodes it runs — building a lasting behavioral link between repeated "I was told first" observations and one persistent I2P identity over time (System 2's core purpose; see below for why this is a structural closure, not a mitigation, and why it holds regardless of adversary size).
- An eclipse-style attacker exploiting the per-IP inbound cap being (incorrectly) shared across a node's multiple local I2P identities (§3.7).
- Tor circuit/session correlation of the kind demonstrated by Biryukov & Pustogarov (*"Bitcoin over Tor isn't a Good Idea,"* IEEE S&P 2015) — mitigated by `-proxyrandomize`'s forced fresh-circuit-per-connection behavior, already in place independent of this work.

**On relay-timing inference specifically:** a directly-connected privacy peer can always observe "I was told about this transaction first" for that one transaction — no design described here changes that single-instance fact. What matters for privacy is whether that observation can be *linked* to anything else. For Tor, it structurally cannot: no persistent identity is ever exposed to the peer, so there is nothing to link a first-told observation to, no matter how many transactions cross that connection. For I2P, prior to System 2, the SAM session's persistent destination *was* linkable across observations; System 2's burn-after-use rotation removes that linkage by construction, not merely by making it harder — an identity is never reused, so a peer's observation about it is a dead end with no second data point to ever compare against. This is the same class of gap that, in the wider ecosystem, motivated Dandelion++ (§4, §6): a lasting per-wallet behavioral profile built from repeated first-told signals.

This closure holds regardless of how many I2P nodes an adversary runs, which is worth stating precisely rather than just asserting: Dandelion's own deanonymization research relies on an adversary embedded in the target's relatively stable peer graph, statistically inferring likely origin from which peer is first-observed more often than chance across *repeated* stem-routed transactions — a stable-vantage-point attack, where controlling more nodes means a better chance of holding that vantage point over time. Burn-after-use rotation denies that vantage point outright: every identity an adversary might observe is indistinguishable from any other node's and never reappears, so there is nothing to accumulate statistics from across transactions no matter how many nodes the adversary controls. Running more I2P nodes still raises the odds of directly witnessing any single transaction (§5's "bare exposure probability" item), but it does not buy the ability to compound that into a profile.

**Does not defend against:**
- **Burst overflow beyond the reserve depth.** Selection guarantees a fresh, never-reused identity per transaction only while `READY` slots are available (§3.5) — bounded by the reserve size. If locally-originated transactions arrive faster than replenishment can keep pace and exceed that depth, [`SelectI2PPoolIdentityForRelay`](../src/net.cpp#L558-L580) falls back to reusing the soonest-draining `ACTIVE` identity, and that identity's connected peers *can* then observe more than one transaction through it before it retires — reintroducing bounded, linkable relay-timing inference for the overflow portion of a burst specifically. This is the one precise case where the closure described above doesn't hold, and it's sized directly by reserve depth: the larger the reserve, the deeper a burst has to be before this triggers.
- **Bare exposure probability from a well-resourced adversary running many I2P nodes.** I2P's total network size is smaller than Tor's, so the anonymity set any individual connection draws from is inherently smaller; an adversary who controls a large fraction of it has a correspondingly higher chance that one of their nodes ends up as a peer of any given pool identity, and directly observes that one transaction's first hop. Rotation doesn't reduce this baseline probability — a pool identity dials or accepts from whatever addrman offers, unweighted against honest vs. malicious addresses — though (see "Defends against" above) it does prevent that exposure from compounding into anything more than a one-off, unlinkable observation.
- **Traffic-watermarking or circuit-tracing attacks below the identity layer** — the kind ProxyMark (§4) demonstrates against Monero, tracing a Tor circuit back to a real IP via watermark injection at malicious entry relays, independent of whether the destination identity is fresh or reused. This system's rotation defeats *identity reuse* as a linking signal; it has no bearing on signal correlation or circuit-tracing at the transport level, which is a different, harder problem belonging to the underlying anonymity network's own design, not to an application built on top of it.
- **Pre-adoption address scarcity.** The pool's outbound warmup depends on addrman holding enough distinct, reachable I2P destinations to dial. Before this design sees meaningful network-wide adoption, the pool of available I2P addresses is smaller than it will become once other nodes are also advertising primary-plus-pool identities — an adoption-dependent bootstrapping property, not a permanent ceiling, but real during any early rollout window.

## 6. Relay-graph obfuscation vs. anonymity-network reliance — why this system chose the latter

§4 surfaces a real design fork the wider ecosystem has taken both ways: Firo and Zano represent close-to-opposite philosophies — Firo obfuscates the relay graph (Dandelion++) explicitly *to avoid* requiring Tor/I2P; Zano rejected the same technique and, after a failed attempt, also backed away from mandatory Tor. Monero and Grin run both an anonymity-network option and Dandelion++ simultaneously, treating them as complementary rather than either being sufficient alone.

This system currently sits on the anonymity-network side of that fork — Systems 1 and 2 both presuppose Tor/I2P connectivity and harden identity behavior within it, without changing the underlying relay graph. That is a reasonable starting point given Pirate Chain's existing Tor/I2P infrastructure, and unlike Dandelion++ elsewhere, it closes the cross-transaction linkability problem by construction rather than by making the "first told" signal statistically less informative — burn-after-use identity rotation doesn't need a global adversary to fail to observe the stem path; it removes the thing being observed. That said, one item in §5 is squarely in Dandelion++'s wheelhouse rather than this system's: burst-overflow reuse, where an already-`ACTIVE` identity relays more than one transaction and its connected peers *can* meaningfully compare "first told" observations again. Stem-routing that overflow case's first hop or two through the privacy-peer subset — rather than announcing directly to every connected peer on the reused identity — would make even a repeated "first told" observation probabilistically uninformative about true origin, the same property Dandelion++ provides elsewhere. It would not help with the other §5 items (adversary scale, sub-identity traffic watermarking, or pre-adoption scarcity), which are different problems at different layers. Following the Monero/Grin/Firo precedent while explicitly avoiding the stempool-design and transaction-chain-handling issues that stalled Bitcoin's own Dandelion proposal, this is a scoped addition worth pursuing specifically for the burst-overflow case, not a general-purpose fix for everything §5 lists.

## 7. Summary

Two systems, addressing two distinct layers of the same problem:

1. **Privacy-peer relay restriction** ensures a locally-originated transaction's first announcement never touches a clearnet peer, closing the raw-IP-exposure gap that exists on essentially every chain that doesn't explicitly guard against it — including, by their own admission, Zcash today.
2. **Rotating I2P relay-pool identities** close a narrower, more specific gap that exists because I2P's SAM protocol — unlike Tor's per-circuit model — ties a persistent identity to a session rather than a stream. This is not a hypothetical concern: Monero's own documentation independently identifies the identical failure mode and mitigates it only by leaning on Tor's circuit churn, a mitigation that doesn't transfer to I2P. Burn-after-use identity rotation, backed by a pre-warmed reserve sized for both staggered-expiry math and burst-transaction depth, is this system's answer to that specific gap.

Neither system claims to solve network-layer privacy completely — §5 is explicit about what remains open: burst-overflow reuse when a rapid succession of local transactions exceeds the pool's reserve depth, the inherent size limits of the I2P anonymity set against a well-resourced adversary, sub-identity traffic-watermarking that operates below where identity rotation can reach, and address scarcity during any early rollout window before the pool sees meaningful network-wide adoption. What neither system leaves open, notably, is the general "I was told first" linkability concern that motivated Dandelion++ elsewhere in the ecosystem: for Tor, no persistent identity was ever exposed to begin with; for I2P, burn-after-use rotation removes it by construction rather than by degree. What both systems together claim is to remove the most direct, currently-exploitable linkability signals available to a network observer today — a real IP, and a reusable identity — using techniques whose trade-offs are already visible in how comparable projects have handled, or explicitly declined to handle, the same problem.
